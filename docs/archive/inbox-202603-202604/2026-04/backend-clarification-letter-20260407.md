## 2. 待澄清的技术细节

### 问题 1: `calls` 数组中的 `target` 解析机制

**场景**: 插件端上传的 `calls` 数组包含函数名，后端需要解析为 `memory_id`。

```yaml
metadata.code_analysis.calls: [
  {"target": "funcB", "line": 42, "column": 10}
]
```

**疑问**: 后端如何将 `"funcB"` 解析为对应的 `memory_id`？

**建议方案**:
- 后端通过 `(project_id, function_name)` 三元组查找（需建立索引）
- 插件端同时提供 `file_path` 和 `target` 以支持跨文件调用

**请确认**: 是否采用此方案？是否需要插件端提供额外字段？

---

### 问题 2: 调用关系双向查询的实现

**确认**: 两个 API 底层都查询 `calls` 表：

```sql
-- references: 谁调用了我
SELECT * FROM calls WHERE OUT = $memory_id

-- dependencies: 我调用了谁
SELECT * FROM calls WHERE IN = $memory_id
```

**疑问**: 
1. 如果调用关系尚未建立（如被调用函数未分析），返回空还是错误？
2. 是否支持递归查询（调用链）？

**请确认**: 第一版是否仅支持单层查询？递归查询是否规划在 Phase 3+？

---

### 问题 3: 代码地图 `file_tree` 数据来源

**场景**: `GET /projects/{id}/map` 返回项目文件树。

**疑问**: `file_tree` 数据来源是？

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. 实时扫描文件系统 | 最新状态 | 可能与记忆数据不一致 |
| B. 从已上传记忆聚合 | 与分析数据一致 | 需要所有文件已上传 |

**建议**: 采用方案 B（从记忆聚合），插件端确保项目文件全量上传。

**请确认**: 是否采用方案 B？是否需要插件端提供文件列表接口？

---

### 问题 4: 复杂度字段命名统一

**发现不一致**:

| 来源 | 字段命名 |
|------|----------|
| 设计文档 v1.4 §6.1 | `min_complexity` / `max_complexity` |
| 后端回复信 | `code_complexity_min` / `code_complexity_max` |

**建议**: 采用设计文档命名（`min_complexity` / `max_complexity`），原因：
- 与现有 `code_complexity` 字段风格一致
- 更简洁，符合 Meilisearch filter 惯例

**请确认**: 是否统一为 `min_complexity` / `max_complexity`？
